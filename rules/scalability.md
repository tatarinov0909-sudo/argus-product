# Масштабируемость — обязательное условие

Перед проектированием и реализацией любой функции сначала проверить, может
ли она работать для множества складов и продавцов без индивидуальной
доработки кода, ручного сопоставления данных командой Аргуса и отдельного
сопровождения каждого клиента. Если нет — такое решение не реализовывать;
сначала найти масштабируемый способ или явно отложить функцию.

- Одна логика для всех клиентов. Нельзя зашивать названия компаний, их ID,
  особенности ассортимента и индивидуальные исключения в рабочий код.
- Подключение выполняется штатным сценарием через настройки и доступы.
  Новая компания не должна требовать разработчика или общения команды Аргуса
  с каждым её продавцом.
- Интеграции используют общие контракты и повторно используемые адаптеры
  для поддерживаемых систем. Отдельная обработка под каждого продавца —
  недопустимая основа продукта. Неподдерживаемую систему нельзя объявлять
  совместимой ради обещания универсальности.
- Оценивать рост объёма данных, запросов, времени обработки и стоимости.
  Использовать постраничное чтение, пакетную обработку, общий серверный кэш,
  ограничение нагрузки и повторов. Открытие кабинета не запускает массовое
  чтение внешнего API для каждого посетителя.
- Отсутствие доступа, данных или фото обрабатывается одинаково для всех:
  понятное состояние интерфейса, без ручной подстановки и угадывания.
- При проверке использовать разные каталоги, длинные названия, большие
  списки и несколько продавцов. Один удачный экран «Слим Тим» не доказывает
  пригодность решения для продукта.
