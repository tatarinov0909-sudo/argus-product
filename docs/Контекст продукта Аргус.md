# Контекст продукта «Аргус»

Обновлено: 10 сентября 2026.

Этот документ фиксирует, для кого и зачем создаётся «Аргус». Он нужен как
опора для решений о продукте, интерфейсах и следующих этапах разработки.
Текущую техническую готовность каждого пункта нужно подтверждать кодом и
проверкой на тестовом контуре: исторические документы описывают и сделанное,
и планы.

## Суть продукта

«Аргус» — операционная система для владельцев фулфилмент-центров, работающих
с продавцами маркетплейсов. Он ведёт товар от поступления на склад до сдачи
в сортировочный центр: приёмка, размещение, хранение, заказы, сборка,
подготовка, отгрузка, возвраты и разбор брака.

Главный результат для владельца фулфилмента — склад работает быстрее и
предсказуемее, а продавцы получают ответы в личном кабинете вместо постоянных
сообщений и звонков менеджеру.

## Кому нужен Аргус

### Владелец фулфилмента

Платящий пользователь. Ему нужны актуальные остатки, понятная схема склада,
контроль операций и инструмент для управления командой и продавцами.

### Селлер — клиент фулфилмента

Пользователь кабинета только для чтения. Он видит только свой товар и всю
информацию, которая отвечает на повседневные вопросы без участия владельца:

- фактический остаток;
- сколько товара уже занято новыми заказами;
- доступное к продаже количество;
- приёмки, отгрузки, возвраты, брак и историю товара;
- документы и выгрузки.

Кабинет не должен давать селлеру возможность менять складские данные или
видеть товары других компаний.

### Складская команда

Кладовщик и менеджер получают простой рабочий поток: принять товар,
разместить его, собрать заказы, подготовить поставку и зафиксировать
отгрузку. Работнику не нужно искать информацию в чатах и не нужно открывать
управляющие функции владельца.

## Контур данных и интеграций

### 1С

1С — действующий источник учётных данных склада. На текущем этапе Аргус
получает из неё данные, не меняет структуру 1С и не записывает в неё
операции. Обмен уже реализован отдельным модулем.

Аргус должен получать из 1С по меньшей мере номенклатуру, складские остатки,
документы, размещение товара и резервы. Изменение 1С и обратный обмен —
отдельный будущий этап, который нельзя предполагать при проектировании
нынешнего функционала.

### Маркетплейсы

Аргус хранит подключённые владельцем ключи API продавцов, чтобы загружать
заказы и связанные данные. Работа с API на первом этапе должна быть только
чтением: продукт забирает заказы и карточки, но не меняет ничего в кабинетах
маркетплейсов.

Ключи — чувствительные данные. Их нельзя показывать после сохранения,
логировать, передавать в браузер без необходимости или выдавать сотрудникам
без отдельного права.

## Складская модель

Владелец видит остатки по складу и карту: зоны, ряды, ячейки и товар в них.
Это основа для операций и будущих подсказок. Данные о фактическом количестве
в ячейке становятся надёжными тогда, когда складские операции проходят через
Аргус; если 1С передаёт только место хранения без количества, Аргус не должен
придумывать распределение остатка по ячейкам.

## Агентная система — главная ценность продукта

Агенты помогают владельцу принимать решения на основе данных склада, но не
заменяют людей в операциях без явного контроля.

### Роли агентов

| Агент | Задача |
|---|---|
| Агент склада | Знает карту, остатки, ячейки и историю движений; отвечает, где искать товар и что происходит с местом хранения. |
| Агент сборки | Предлагает порядок подбора и маршрут по ячейкам для конкретной волны заказов. |
| Агент-логист | Помогает планировать поставки, маршруты, загрузку машин и окна приёмки маркетплейсов, когда в системе есть необходимые данные. |
| Главный агент-архитектор | Принимает вопрос владельца, определяет, какому специализированному агенту нужна задача, объединяет результаты и объясняет рекомендацию. |

### Границы автономности

- Агент даёт рекомендации и готовит задания; операции с остатками, отгрузками,
  доступами, API-ключами и деньгами требуют явного действия человека.
- Агент не общается напрямую с селлером и не заменяет его кабинет.
- Агент работает только с данными конкретного склада и в пределах прав
  пользователя, который задал вопрос.
- Расход вычислительных ресурсов ограничивается на серверной стороне:
  маршрутизация простых запросов без модели, лимиты на задачи и бюджеты,
  кэширование результатов, журнал вызовов и подтверждение дорогих действий.

Эти ограничения — часть внутренней архитектуры Аргуса. Пользовательский
интерфейс должен показывать полезный результат, а не механику расхода токенов.

## Коммерческая модель

Аргус позиционируется как дорогой B2B-сервис, потому что заменяет заметную
часть ручной координации склада и снижает стоимость ошибок. Тарифы, единица
тарификации и точные цены пока не утверждены. В стоимость должны входить
понятные для владельца результаты: управление складом, доступ продавцов,
интеграции и агентная помощь в согласованном объёме.

## Отдельный лендинг

Маркетинговый лендинг — отдельный сайт и отдельный проект. Его задача —
продавать технологичность и ценность Аргуса, а не повторять интерфейсы
операционной системы. Визуальное направление, референсы, содержание и воронка
будут утверждаться отдельным документом после получения материалов.

## Критические условия запуска кабинета селлера

1. Каждая операция и остаток должны быть однозначно привязаны к продавцу.
   Пока в исходных данных есть общая компания-заглушка, доступ селлера нельзя
   открывать на её данные.
2. Доступ продавца должен быть технически изолирован на уровне сервера и базы,
   а не только скрыт в интерфейсе.
3. Данные о заказах, резерве и остатке должны иметь время последнего
   обновления, чтобы пользователь понимал актуальность цифр.
4. Перед показом "доступно к продаже" требуется согласовать точную формулу и
   источники резервов, чтобы не обещать товар, уже занятый заказом.

## Открытые решения

- Что является первой платной версией: кабинет селлера, экран менеджера
  заказов или первый агентный сценарий для владельца.
- Как и когда изменится модуль 1С, чтобы в обмене появилось корректное
  разделение по продавцам, резервы, штрихкоды и при наличии — габариты.
- Какие маркетплейсы запускаются после Wildberries и какие права их ключей
  нужны для карточек товара.
- Какие данные нужны для Логиста: машины, водители, тара, размеры ячеек,
  окна поставок и карты.
- Как будет устроен биллинг и цена подписки.
- Какие референсы определят визуальный язык отдельного лендинга.

## Ближайшая продуктовая гипотеза для обсуждения

Первый завершённый сценарий: владелец подключает продавца и его ключ
маркетплейса, данные разделены по этому продавцу, а продавец открывает личный
кабинет и сам видит остаток, новые заказы, доступное количество, движения и
документы. Это снижает нагрузку на владельца сразу и создаёт надёжную основу
для агентов, потому что они получают чистые данные по товару и операциям.
