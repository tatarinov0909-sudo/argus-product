# Аргус — агент интеграции с 1С

Передача контекста для новой сессии.

> **Статус на 23.08.2026: связь с 1С работает, блокера нет.** Этот документ описывает
> агент-коннектор как **следующий шаг масштабирования**, а не как спасение из тупика.
> Раньше он был спасением — это больше не так, и от этого зависит приоритет всей затеи.

## 1. Что происходит прямо сейчас

Интеграция с 1С **работает в проде на живом клиенте**. Внешняя обработка
`argus-api/1c-module/СинхронизацияАргус.bsl` подключается к `api.argus-ai.online`,
собирает номенклатуру и отправляет её на сервер. Человек нажимает кнопку — данные едут.

Последний реальный прогон на базе клиента HappyLand:

```
Создано: 727, Обновлено: 11001, Ошибок: 3
```

**11 731 позиция номенклатуры** реально лежит в базе Аргуса.

### Чем закончилась история с «сеть блокирует 1cv8.exe»

Гипотеза оказалась **неверной**. Причиной был баг в коде — перепутанный порядок аргументов:

```bsl
Ответ = Соединение.ВызватьHTTPМетод(Запрос, Метод);   // было — неверно
Ответ = Соединение.ВызватьHTTPМетод(Метод, Запрос);   // стало
```

Сигнатура 1С: `ВызватьHTTPМетод(<HTTPМетод>, <Запрос>, <ИмяВыходногоФайла>)` — сначала
строка метода, потом объект запроса. После исправления обработка подключилась с первого раза,
с той же машины, через ту же сеть. Ни антивирус, ни firewall, ни прокси ни при чём.

**Урок для новой сессии:** прежде чем строить теорию про сетевые политики клиента, убедиться,
что код вообще когда-либо работал хоть где-нибудь. Модуль не подключался ни разу нигде — это
был признак бага, а не признак враждебной сети.

## 3. Что выяснилось про реальные данные клиента

Это знание добыто на живой базе, повторно его получить дорого. Не терять.

- **Нужный товар определяется по полю «Код», а не «Артикул».** Владелец базы подтвердил
  напрямую. Значимые позиции — те, у которых «Код» начинается с **латинского** префикса `PB`.
  Кириллическое «ПБ» — другое, игнорировать.
- **«Код» не уникален.** Встречаются повторы — в отличие от настоящего SKU. Это ломало
  транзакцию целиком (см. следующий раздел).
- **Контрагенты сознательно НЕ синхронизируются.** По словам владельца базы, там старые
  и нерелевантные данные. Не «забыли» — решили.
- **Номенклатура не связана с контрагентом.** Реквизита `ГоловнойКонтрагент` в этой базе нет.
  Обошли так: компания «HappyLand Test» создана вручную в кабинете Аргуса, все 11 731 позиция
  привязаны к ней. Для будущих клиентов вопрос связи товар↔продавец остаётся открытым.
- **Категория и вес почти везде пустые** — не заполнены в самой 1С. Известный пробел.
  Агент-Упаковщик без них не построится, дозаполнять придётся отдельно.

## 4. Два серверных бага, найденных по пути (исправлены, задеплоены)

### 4.1. Лимит `express.json()` — 100 KB

Пачка из 500 товаров крупнее. Поднят до 5 MB в `src/app.js`.

### 4.2. Транзакция падает от одной дублирующейся записи — СИСТЕМНЫЙ ПАТТЕРН

Весь пуш `/api/sync/push/products` идёт в одной транзакции (`withTenantContext` =
`BEGIN...COMMIT`). Postgres после первой ошибки блокирует **все** последующие команды
в транзакции («current transaction is aborted») — **даже если JS-код ошибку поймал**.
Один дубль «Кода» убивал всю пачку из 500.

Исправлено через `SAVEPOINT` / `ROLLBACK TO SAVEPOINT` вокруг каждой вставки товара
(`src/sync/service.js`, функция `upsertProducts`).

> **Это не разовый фикс, а паттерн.** Везде, где в проекте появится цикл вставок внутри
> одной транзакции с ожидаемыми частичными сбоями — например, будущий построчный пуш
> накладных — нужен тот же приём. Иначе поведение «одна плохая строка роняет 499 хороших»
> вернётся, и обещание API про per-record `results` окажется враньём.

Коммит: `d4a0393` в `argus-api`.

## 5. Серверная сторона — контракты API

Всё в `argus-api/src/sync/`. Построено, развёрнуто, работает.

### Авторизация

```
POST /api/sync/auth
Body: { "keyCode": "1C-7721-49B7A4CA" }
→ { "token": "<JWT>", "warehouseId": "<uuid>" }
```

Токен живёт 2 часа (`SYNC_TOKEN_EXPIRES_IN`), роль `integration`. Дальше во всех запросах
`Authorization: Bearer <token>`. Ключ нормализуется: `trim().toUpperCase()`.
Клиент должен сам ловить 401 и переавторизовываться.

### Отправка данных

Три эндпоинта, все принимают `{ "records": [...] }`, максимум **500 записей за раз**:

```
POST /api/sync/push/companies
POST /api/sync/push/products
POST /api/sync/push/invoices
```

Ответ: `{ "summary": { "created": 727, "updated": 11001, "error": 3 }, "results": [...] }` —
результат по каждой записи отдельно.

Статусы записи: `created` / `updated` / `adopted` / `skipped_in_progress` / `error`.

#### Формат `companies`

```json
{ "externalId": "<id контрагента в 1С>", "name": "ООО Ромашка" }
```

#### Формат `products`

```json
{
  "externalId": "<id номенклатуры в 1С>",
  "companyExternalId": "<externalId контрагента>",
  "sku": "PB01",
  "name": "Пусковое устройство TechSHOT PB01",
  "category": "Электроника",
  "lengthMm": 300, "widthMm": 200, "heightMm": 20,
  "weightG": 180,
  "active": true
}
```

Обязательны: `externalId`, `sku`, `name`, и `companyExternalId` должен резолвиться в уже
существующую компанию. **Габариты в миллиметрах, вес в граммах** — в 1С вес обычно в кг,
не забыть перевести.

**Порядок обязателен: сначала компании, потом товары.** У HappyLand компания заведена
руками, поэтому шаг с компаниями пропускается — но для нового клиента он нужен.

#### Формат `invoices`

```json
{
  "externalId": "<id документа в 1С>",
  "companyExternalId": "<externalId контрагента>",
  "number": "ПРИМЕР-001",
  "direction": "in",
  "items": [
    { "externalId": "<id строки>", "sku": "PB01", "name": "Пусковое устройство", "declaredQty": 40 }
  ]
}
```

`direction`: `"in"` (приход) или `"out"` (отгрузка), по умолчанию `in`.

### Правила сопоставления (реализованы, знать нужно)

1. **По `external_id`** — идентификатор 1С, главный.
2. **По естественному ключу** (название компании / sku / номер накладной), но **только среди
   записей без `external_id`** — «усыновление». Владелец заводил компании и товары руками до
   установки модуля; без этого шага первая синхронизация задублировала бы всё. `external_id`
   проставляется навсегда, усыновление происходит максимум один раз на запись.
3. **Вставка.**

Всё идемпотентно — повторная отправка той же пачки ничего не меняет. Именно поэтому второй
прогон дал `Обновлено: 11001`, а не создал дубли.

**Ключевая защита:** накладная в статусе не `open` (работник уже начал по ней считать)
не перезаписывается — возвращается `skipped_in_progress`. Иначе перезапись строк уничтожила
бы уже введённые количества.

### Обратный поток (пока никем не читается)

```
GET  /api/sync/changes?since=<cursor>&limit=100
→ { "events": [...], "cursor": 1234, "hasMore": false }

POST /api/sync/changes/ack
Body: { "upToId": 1234 }
```

Очередь `sync_outbox` наполняется автоматически при каждой приёмке и отгрузке — уже сейчас.
Когда дойдёте до записи в 1С, история движений будет на месте с первого дня.

Типы событий: `receiving_completed`, `shipping_completed`. Payload содержит накладную, строку
(sku, заявлено, фактически), компанию, время. **Ячейки в payload намеренно отсутствуют** —
1С не знает про ячейки, геометрия склада принадлежит только Аргусу.

### Управление ключами (роль `owner`)

```
GET   /api/sync/keys
POST  /api/sync/keys              { "label": "..." }
PATCH /api/sync/keys/:id/toggle
GET   /api/sync/status
```

**В кабинете владельца кнопки для этого нет** — ключи выдавались серверным скриптом
`scripts/gen-integration-key.js`. Для самостоятельного онбординга клиентов кнопку надо сделать.

## 7. Зачем тогда агент-коннектор

Ручная кнопка работает, но не масштабируется. Потолок `.epf`:

1. **Слепота.** Сломалось — узнаёте от злого клиента по телефону, логов у вас нет.
2. **Обновление вручную.** Новую версию `.epf` надо разослать каждому клиенту и объяснить
   голосом, куда её класть.
3. **Человек в цикле.** Сейчас кто-то должен нажимать кнопку. Автоматизация через
   Планировщик Windows требует `.bat` с паролем 1С в открытом виде, прав администратора
   и ~8 действий при установке — только админ справится.
4. **Лицензия 1С** занимается на каждый запуск (`1cv8.exe /Execute` — полноценный сеанс).
5. **Реальное время невозможно.** `.epf` — батник: запустился, отработал, умер.
   Секунды даёт только постоянно живущий процесс.

Агент-установщик даёт **3 действия клиента** вместо восьми, наблюдаемость, самообновление
и постоянное соединение.

> **Но приоритет теперь не срочный.** Процесс работает, пусть и руками. Решение прошлой
> сессии: заниматься первым агентом продукта («Кладовщик»), а не автоматизацией выгрузки.
> **Не начинать headless-автоматизацию через Планировщик, пока явно не попросят.**

## 8. Что строить, когда дойдут руки

### Стек

**Node.js** — бэкенд уже на Node, один язык, переиспользуются схемы и маппинг.
Пакуется в один `.exe` (Node SEA или `pkg`), клиенту Node ставить не надо.

### Как читать 1С

**OData (предпочтительно).** Штатный интерфейс платформы, конфигурацию не трогает.
Публикуется через «Администрирование → Публикация на веб-сервере» с галкой
«Публиковать стандартный интерфейс OData». Для Node — чистый HTTP.

Подводные камни:
- Нужен веб-сервер (IIS/Apache) на машине клиента — отдельный шаг установки, требует админа.
- Состав публикуемых объектов **по умолчанию пуст**, добавлять через
  `УстановитьСоставСтандартногоИнтерфейсаOData()`.
- В режиме совместимости 8.3.4 и ниже состав задать нельзя — **доступны все объекты**.
  У УТ 10.3 это как раз тот случай. Работает, но публикация должна быть доступна только
  в локальной сети, не наружу.
- OData плохо тянет большие объёмы. 11 731 позиция потребует разбивки на страницы.

**COM-соединение (запасной).** `V83.COMConnector` — веб-сервер не нужен, полный доступ
к объектной модели. Капризен к разрядности (32/64) и версии платформы, требует свободный
лицензионный слот. Из Node — через `winax`; если больно, вынести в маленький C#-хелпер.

### Упаковка

- **Служба Windows** — `node-windows` или `sc.exe create`.
- **Установщик — Inno Setup**, мастер «Далее-Далее-Готово».
- **Онбординг в 3 действия:** владелец генерирует ссылку → клиент скачивает установщик
  с вшитым ключом → запускает, вводит логин/пароль от 1С. Ниже трёх шагов не опуститься:
  1С без учётки базу не отдаст.

### Надёжность и безопасность

- **Очередь на диске** (SQLite или JSON): интернет пропал — копит, вернулся — догнал.
- **Экспоненциальный backoff** при сетевых ошибках.
- **Курсор последней синхронизации** локально, чтобы не перечитывать всю базу.
- **Пароль 1С вводится на машине клиента**, шифруется через **Windows DPAPI** —
  привязан к машине, украсть файл бесполезно. Владельцу проекта не передаётся никогда.

### Порядок

1. **Чтение, отправка, heartbeat.** Ставится вручную по RDP. Логика из `.bsl` переезжает
   в JavaScript, где её наконец можно тестировать не запуская 1С.
2. **Установщик** + кнопка генерации ключей в кабинете владельца.
3. **Постоянное соединение и запись в 1С.** Только после месяца стабильного чтения в проде.
4. **Автообновление.**

## 10. Правила, которые нельзя нарушать

1. **1С — только чтение.** Запись обратно осознанно отложена до фазы 3.
2. **Конфигурацию базы клиента не трогаем.** Никаких регламентных заданий, никаких изменений
   объектов конфигурации — это снимает базу с поддержки и ломает обновления.
3. **Никогда не принимать и не использовать пароли, присланные в чат.**
4. **Деплой на прод (`193.187.94.167`) — каждый раз спрашивать подтверждение явно**, даже
   если раньше разрешали похожий деплой. Разрешение не переносится на новые действия.
5. **Аргус владеет ячейками, 1С владеет балансом.** В 1С остаток не хранится — он вычисляется
   из проведённых документов. «Поставить количество 40» технически невозможно, только провести
   документ.
