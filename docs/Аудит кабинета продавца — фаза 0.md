## Главное: остаток и сборка пока расходятся со спецификацией

В `argus-api/src/sellers/routes.js:116` значение onHand берётся из 1С,
если оно доступно. Только при отсутствии значения используется годный остаток
ячеек. Требование пользователя другое: ячейки Аргуса — основной источник,
1С — отдельная сверка.

Простая замена источника не исправит весь сценарий. В
`argus-api/src/shipping/routes.js:201` товар списывается из ячеек при подборе.
Заказ становится ready, но до фактического отъезда остаётся в ordered.
При отсутствии значения 1С возникает двойное вычитание.

Пример: было 100, заказ на 30. После подбора в ячейках 70, в заказах 30,
сервер показывает доступно 40. Физически свободны 70, ещё 30 стоят у ворот.
После смены статуса на shipped доступное снова возрастёт до 70.

Рекомендуемая модель для согласования: зона готовых заказов учитывается как
место хранения в Аргусе. Подбор переносит товар туда, отгрузка списывает его
со склада. Тогда до отъезда «На складе» = 100, «В заказах» = 30,
«Доступно» = 70; после отъезда 70 / 0 / 70. Это предложение,
а не уже реализованное или утверждённое изменение.

Нельзя дополнительно вычитать все резервы 1С поверх всех заказов: один заказ
может присутствовать в обоих источниках. Нужна связь обязательств, чтобы
исключить двойной учёт. В текущем seller stock SQL поле reserved_qty и таблица
stock_reservations не используются. Поиск по src нашёл обращения к
stock_reservations только в её миграции.

При нехватке текущий сервер ограничивает available нулём, а дефицит отдаёт
отдельным short. Пользователь описал арифметическую разность; политику
отрицательных значений нужно явно закрепить до изменения формулы.

## Дополнительные расхождения

1. **Нулевая сверка 1С теряется.** В `src/sellers/routes.js:72` каталог
   отфильтрован условием ненулевого остатка 1С. Известный ноль превращается
   в отсутствие данных при соединении с ячейками. Строка сверки может
   исчезнуть именно тогда, когда в Аргусе товар есть, а в 1С уже ноль.
2. **«Уехало» включает подбор.** В `src/sellers/routes.js:159` движения
   формируются из shipping_records без проверки shipped у накладной.
   finished_at — время подбора, не отъезда. Отдельный факт отъезда есть
   в обработчике `src/shipping/routes.js:298`, но для ленты требуется
   надёжная дата отгрузки.
3. **Менеджер не может выбрать продавца в этих двух маршрутах.**
   /stock и /movements разрешают роль manager, но query.companyId
   читается только для owner. У менеджера нет companyId в токене,
   результат — 400. Для кабинета селлера это не блокер, для просмотра
   менеджером — отдельная доработка.
4. **Сводная сверка может скрывать ошибки товаров.** Фронтенд сравнивает
   общую сумму ячеек с общей суммой 1С. Расхождения +4 и -4 по разным
   товарам взаимно погашаются. Нужно отдельно учитывать число
   несовпадающих позиций и полноту данных 1С.

## Изоляция продавцов

В коде есть необходимая основа: tenantContextFromAuth() передаёт для seller
только companyId, а не доступ ко всему складу. Миграции включают RLS
для остатков, товаров и документов. Это подтверждает устройство кода,
но не применение миграций и прав на рабочем сервере.

Нужно отдельно проверить:
- приложение подключается ролью без обхода RLS и владения таблицами;
- два продавца одного склада не читают данные друг друга, включая прямые ID;
- реальные накладные, остатки и номенклатура имеют правильного владельца;
- общая компания не выдана продавцу как его личный контур.

Обработчик выдачи ключа проверяет существование компании, но отдельного
признака «данные этой компании сверены и готовы к доступу продавца» не видно.
Историческую общую компанию нельзя считать устранённой по одному наличию RLS.

## 1С и штрихкоды: исправление старого контекста

Текущий модуль уже содержит чтение barcode и reservedQty
(`1c-module/СинхронизацияАргус.bsl:522`) и контрагента документа
(`:684`). Поэтому заявления старых документов «модуль не умеет»
не являются текущим фактом.

Однако у номенклатуры companyExternalId оставлен неопределённым (`:518`),
при отправке используется defaultCompanyName, а автозапуск намеренно
пропускает отправку контрагентов (`:1714`).
Это требует проверки согласованности каталога, документов и остатков.
Наличие кода чтения штрихкодов не подтверждает заполненность живой базы.

Штрихкод — кандидат для сопоставления, а не гарантия совпадения:
нужны проверки дублей, вариантов товара, упаковок и единиц измерения.
Нельзя обещать универсальный файл, принимаемый любой 1С без настройки.
Также нельзя автоматически записывать «доступно к продаже» как физический
бухгалтерский остаток продавца: назначение поля/документа импорта ещё
предстоит согласовать на конкретной конфигурации.
