# Обмен остатками с 1С продавца

Статус на 11.09.2026: формирование и проверка файла реализованы в API.
Добавлено исполняемое общее ядро предварительной проверки импорта, без записи.
Загрузчика в 1С нет; импорт в реальную конфигурацию не проверен. В 1С склада
или продавца этот механизм ничего не записывает.

## Решение для нескольких продавцов у каждого фулфилмента

Аргус выпускает один версионированный файл `argus.inventory` v1 (UTF-8 JSON).
Совместимый загрузчик на стороне продавца определяет конфигурацию, проверяет
поддержку и загружает значения через соответствующий адаптер. Владелец
фулфилмента не должен выяснять версии 1С продавцов или менять настройки
выгрузки для каждого клиента.

Свой формат не является стандартным документом 1С или CommerceML. Наличие
в платформе [чтения JSON](https://v8.1c.ru/platforma/json/) позволяет разобрать
файл, но не задаёт соответствия реквизитов, регистров и документов конкретной
конфигурации. [Внешняя обработка](https://v8.1c.ru/platforma/vneshnie-obrabotki/)
может стать способом доставки загрузчика, когда окружение продавца это
разрешает. Обещание «работает со всеми версиями 1С» до такой проверки неверно.

## Контракт v1

Машинная схема хранится в API: `docs/argus-inventory-v1.schema.json`.

| Поле | Значение |
|---|---|
| format / schemaVersion | `argus.inventory` / `1` |
| seller.id / warehouse.id | UUID компании и склада в Аргусе; область действия снимка |
| seller.name | Название для проверки человеком, не ключ сопоставления |
| snapshotId | SHA-256 канонического содержимого; повторная выгрузка без изменения содержания имеет тот же ID |
| generatedAt | Время формирования UTC; не время последней синхронизации с 1С |
| quantityMode | `absolute`: значения снимка, не приход и не прибавка |
| missingItems | `unchanged`: отсутствующие товары не обнулять |
| primaryMeasure | `available`: назначение для наличия в продаже, не бухгалтерский остаток |
| items[].sku | Артикул Аргуса; не внутренний код номенклатуры продавца |
| items[].barcode | Строка, включая ведущие нули; исходный идентификатор сопоставления |
| items[].unit | `pcs`, штуки; упаковки автоматически не пересчитывать |
| items[].onHand | Годное в ячейках плюс подобранное и ещё не отгруженное |
| items[].inAssembly | Всё количество в неотгруженных заказах |
| items[].available | max(0, onHand − inAssembly) для этого товара |
| items[].stockObservedAt | Последнее известное складское событие/обновление ячеек; не подтверждение свежести внешнего обмена |

Снимок содержит все SKU компании независимо от фильтра интерфейса. Неизвестный
остаток, пустой список, отсутствующий/повторяющийся штрихкод или количество,
которое нельзя представить целым неотрицательным безопасным числом, блокируют
всю выгрузку. Неполный файл, который выглядит полным, не выпускается. Известный
ноль разрешён. Источник 1С не подставляется вместо количества в Аргусе.

`GET /api/sellers/export/1c` возвращает результат проверки. С `?download=1`
возвращается снимок либо HTTP 422 с замечаниями. Используется обычная
авторизация продавца; переданный им companyId не меняет область доступа.
Ключи API, токены и ключ входа в файле отсутствуют.

## Обязательные правила будущего загрузчика

1. Проверить формат, версию, схему, допустимые количества и семантику полей.
   Для неизвестной версии завершить работу с понятным сообщением.
2. Один раз связать компанию/склад Аргуса с организацией/складом продавца.
   При смене источника запросить явный выбор, не использовать первый склад.
3. Сопоставить штрихкод с номенклатурой, характеристикой и единицей. Ноль или
   несколько совпадений — замечание, а не автоматическое создание дубля.
4. Показать предварительный результат, изменения и несопоставленные строки.
   Запись допустима только после успешной проверки всего снимка.
5. Для продаж использовать `available`; не записывать его автоматически в
   бухгалтерский или физический регистр. Куда и каким документом записывать
   `onHand`, определяет отдельный проверенный адаптер конфигурации.
6. Повторный snapshotId не создаёт второй документ. Хранить журнал по паре
   seller.id + warehouse.id. Более старый generatedAt блокировать относительно
   последнего применённого снимка; допустимый возраст файла — настройка
   интеграции. Сам snapshotId не является цифровой подписью.
7. Импорт атомарный: ошибка не оставляет половину строк. Не складывать
   абсолютные значения с существующими, не менять товары вне снимка.
8. До заявления совместимости проверить на отдельной базе каждой поддерживаемой
   конфигурации: загрузку, повтор, старый файл, разные склады, нули, брак,
   характеристики, упаковки, неоднозначные штрихкоды и откат после ошибки.

Эти пункты — требования к следующему этапу, не описание уже существующей
обработки. Для 1С 7.7, старых платформ, облачных и изменённых конфигураций
совместимость устанавливается отдельно; универсального готового загрузчика
для них в этом релизе нет.

## Реализованная предварительная проверка

В API добавлены `tools/inventory-import/plan.js`, CLI и искусственный пример
контекста адаптера. Инструмент запускается локально на Node.js, не подключается
к 1С и не меняет данные. Он проверяет структуру v1, контрольный хеш реального
экспортера, формулу трёх количеств, связь источника и назначения, повторы и
устаревшие снимки. Допустимый возраст файла, складских наблюдений и каталога
назначения задаётся явно; новая дата скачивания не делает старый остаток свежим.

Каталог назначения передаётся будущим адаптером одной конкретной базы,
организации и склада. Сопоставление штрихкода точное, строковое, с учётом
характеристики и единицы. Несколько совпадений, несколько исходных строк на
одну целевую позицию или упаковка вместо штуки блокируют весь план.
Подмена `onHand` данными 1С и автоматическое обнуление отсутствующих строк
не выполняются.

Успешная проверка возвращает только план абсолютных изменений доступности
продаж. Это не разрешение на запись и не готовый импорт 1С. Адаптер должен
в транзакции перепроверить журнал и исходное состояние назначения, применить
изменения вместе с журналом атомарно. Подробный вход и запуск описаны в
`argus-api/tools/inventory-import/README.md`; проверки —
`argus-api/test/inventory-import-planner.test.js`.

Следующий этап — реализовать чтение и запись через один адаптер выбранного
семейства конфигураций и испытать его на отдельной базе. Общие правила
проверки используются всеми продавцами без разработки под каждого клиента.
